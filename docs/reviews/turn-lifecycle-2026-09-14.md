# Cancellation, undo and regeneration review — 2026-09-14

## Scope and entry points

The working tree was clean at the start. This review follows the character
lifecycle review of the same date. No application, Electron, browser or UI/E2E
runner was launched.

| Action | Entry point | State policy |
| --- | --- | --- |
| Stop / cancel | `App.cancelRunOrUndoLastTurn`, `useRunLifecycle.cancelCurrentRun`, `useGraphRun.runGraph` | Abort signal; before delivery, remove collected messages and restore attempt runtime; restore the submitted draft. Once output delivery is complete, cancellation of next-turn preparation keeps the delivered turn. |
| Restart an active run | `App.regenerateLastOutput`, `pendingRunRestart`, `finishRun` | Abort the current attempt and queue its retry after cleanup. Restart during preparation rolls back the attempt too. |
| Undo one or multiple turns | `App.undoLastTurn`, `useTurnRecordState.applyTurnCheckpointRuntime` | Each click removes the last turn's input/output messages, checkpoint and trace; restores checkpointed node state/variables; restores notes/ChatGPD records and action-choice visibility. Multiple clicks repeat this operation. |
| Regenerate completed output / edited input | `App.regenerateLastOutput`, `App.regenerateEditedMessage`, `useGraphRun.runGraph` | Validate first, then restore the prior checkpoint, collect replacement output and replace the turn/checkpoint. A failed attempt restores the exact runtime present before replacement and the old messages. |
| Direct app actions | `useDirectAppActions`, `useTurnRecordState.commitLocalAppTurn` | Structured history transactions. Bank transfers, note/chat actions and MatchMe matches are represented in turns; MatchMe match creation is explicitly excluded from LLM regeneration. |
| Autoplay | `useAutoplay` | Can stop scheduling and cancel an active autoplay run; no suspended graph continuation. |
| Complete Last Run / graph pause | No current entry point found | These are not available actions in this checkout. Prepared-node reuse is not a separate resume command. |
| Save / load / reset RP | `App.currentSession`, `applyLoadedRpgraphFile`, `applySessionFile`, `commitHydratedWorkflow` | Serialize committed timeline, checkpoints, runtime, app state and pinned NPC archive. Loading hydrates and validates before replacement. Replacement and RP saving are now rejected while a run is active. |

Manual Storybook creation/import, promotion, retirement, deletion and authoring
are currently outside the turn timeline. Manual likes, follows and paid-post
unlocks also write separate saved app state. Authored starting relationships and
initial posts are configuration, not interactions generated by a turn.

## Fixed findings

### Storybook checkpoints overwrote later authoring and character lifecycle changes

Reproduction: a turn updates the Storybook, the user retires/deletes a character
or edits its definition, then undoes that older turn. Whole-document restoration
could reactivate the character or overwrite its newer definition.

`restoreStorybookCheckpoint` applies a three-way comparison of the live document
and the checkpoint's source and target. Unchanged fields are left alone; changed
fields are restored only while the live value still matches the source. Character
arrays are matched by stable ID, with each character treated atomically. New
manual imports, later edits, order and absent characters survive. Treating entire
characters atomically avoids creating hybrid account/gallery/relationship
payloads. Other top-level Storybook fields are also atomic.

Both Storybook node types, in-memory and saved checkpoints, and both restore
directions use this policy. No old checkpoint is rewritten. Invalid current JSON
is preserved when it conflicts with the checkpoint. NPC archives remain separate
from activity and retain their existing immutable-revision policy.

A deliberately conservative limitation: editing a character after a turn also
preserves that character's turn-generated fields, rather than guessing which
parts of the edited payload are safe to remove. Identical manual rewrites cannot
be distinguished from unchanged values without authoring provenance metadata.

### Provider preflight was not fully part of the run lifecycle

The active-run ref was set before the health-check await, but the visible running
state was only set afterward. Abort could still proceed into setup; a thrown
health check could strand the active run. Regeneration callers had already
rewound runtime before endpoint/provider validation.

The running state now includes preflight, abort is checked on resolution, failures
clean up and restore ordinary input drafts, and queued restarts wait for cleanup.
Regeneration rewind now happens centrally after successful preflight. Failure of
a replacement restores the captured live runtime, rather than replaying an old
checkpoint over possible later authoring.

### Late asynchronous results and delayed node decoration could write after cancellation/undo

`NodeLlmApi` now rejects replies that resolve successfully after abort, drops late
stream/reasoning updates and checks abort after connection resolution. ComfyUI
character-image generation checks abort before dispatch and before publication
into the Storybook. External generation may still finish remotely; its result is
not attached to the RP after abort.

The minimum-duration node-active timer used to replay the entire completion
patch, even though its data had already been applied immediately. Undo within
that interval could be overwritten. The timer now writes only `runActive: false`.
Live output scheduling also ignores aborted/inactive runs.

### RP replacement and Storybook authoring could race with a live run

Runtime rollback restores attempt snapshots and therefore needs exclusive
ownership during a run. File application/reset, RP serialization and manual
Storybook commits now reject an active run, including provider preflight.
Storybook lifecycle checks use the synchronous active-run ref as well as the
rendered state. The block lasts until cancellation cleanup actually completes.
RP serialization captures workflow, runtime and app state without yielding between
them. This is a targeted transaction boundary, not an Undo lock.

### Automatic account-link contacts became permanent after save/load

Reproduction: send a message sharing an account with a simulated recipient; save;
reload; undo that message. The merged manual-plus-automatic contact view was saved
and loaded as manual state, so the automatic grant survived Undo.

New RP saves serialize only the saved/manual contact basis. Automatic account-link
grants are recomputed from the loaded timeline and disappear with their source
messages. Explicit manual contacts remain. Opening History import retains its
existing configured initial-state semantics.

Legacy saves already contain merged contacts without origin metadata. They remain
compatible, but cannot safely be stripped automatically: a contact can also have
been added intentionally. No speculative migration is performed.

### NPC Library conflated activity with snapshot retention

A retained NPC with no remaining activity is now in Available Characters, with
its RP snapshot provenance still visible. Interacted Characters and its statistic
only use actual reference detection; a snapshot alone no longer qualifies. The
archive is intentionally not erased when the last interaction is undone.

## Round 12 back to round 8: requested lifecycle semantics

For a timeline MatchMe match/message introduced in round 10, removing the relevant
turns removes that activity. Starting matches authored in relationships are
independent configuration and remain. A pinned NPC revision remains available for
a consistent retry, without itself proving acquaintance. New saves also preserve
the reversibility of automatic account-link contact grants.

**Confirmed policy:** making an NPC playable is manual authoring and remains in
place when conversation turns are undone. The user confirmed that manually
removing the character from the playable cast afterward is sufficient. Use
Remove / keep as NPC to retain the revision and its references, or delete when
unused. No extra lifecycle transaction or first-contact coupling is introduced.
This keeps later manual edits and cast membership independent of turn rewind.

## Other boundaries and open decisions

- Manual likes, follows and OnlyFriends unlocks are not individual Undo turns.
  Rewinding conversation does not remove these independent manual actions. If
  all app actions must follow the same chronological rewind, they need explicit
  transactions and save/Opening History support, not pruning based on names.
- Derived dynamic social users are saved as directory state. Removing a message
  may leave a non-container fictional directory identity after reload. Its
  lifetime needs a separate policy; it is not a pinned character's playable state.
- Only the latest 50 checkpoints are retained, while older timeline turns can
  remain. Undo of a turn whose checkpoint was trimmed only removes activity,
  without restoring historical node runtime. Choosing a visible Undo boundary or
  retaining more history is still required for guaranteed arbitrarily deep Undo.
- During cancelled next-turn preparation, completed preparation changes are kept
  with the delivered turn. Stop is not a rollback of already delivered output.
- IDs are not regenerated by checkpoint restoration. Existing NPC tests cover
  stable aliases, account IDs, image IDs and ownership-scoped initial-post keys
  through promotion/retirement and absent library files. External file saves and
  external provider work are not undone by RP Undo.
- Interactive rendering, selection, remote providers and packaged-app behavior
  remain for manual validation. This is a focused review, not a proof of every
  possible asynchronous UI callback.

Regression coverage includes both Storybook node types, saved checkpoints,
retirement/deletion and manual edits/imports, two consecutive undos followed by
RP serialization/reload with pinned media, provider cancellation/failure/restart,

TypeScript files, and whitespace/diff check. No UI or application launch.
