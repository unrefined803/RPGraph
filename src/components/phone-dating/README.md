# MatchMe integration

MatchMe retains its phone layout and dark theme. It uses the shared social DM
workflow and timeline; UI components never open their own LLM connection.
Every like immediately creates an active mutual match. This rule lives in
`chat/matchMe.ts` as `matchMeLikePolicy`, ready to replace with another policy.
There is no background message timer.

## Accounts and persistence

`chat/datingAccounts.ts` contains four stable fictional NPC accounts with public
profiles and private personalities for legacy/demo compatibility. Effective
Storybook, library and pinned-snapshot characters with MatchMe profiles are
projected through the shared registry, with ordered gallery photos and their own
characterization and public cross-app metadata. Matching names never link an NPC to a Storybook
character or merge conversations. Canonical container account IDs are preserved;
node-scoped `storybook:` IDs remain read aliases and legacy `demo-*` NPC account
IDs remain stable.

The `plotTwist` profile field and `plottwist` phone layout key remain compatible.
Profiles store public fields, photo references, decisions and a migration version.
They no longer maintain live conversation history. Structured `matchMeMatch`
timeline records contain the deterministic pair ID, both account IDs, timestamp
and status. Each new match has one readable history event in the same record.
Removing those records by restoring an earlier history removes the permission;
visible history text never creates a match. Local match actions use the shared
turn/checkpoint transaction and cannot be regenerated by the LLM.

Loaded legacy profiles are migrated once while idle. Existing likes create
structured matches, and saved demo conversations are retained even if the old
Explore again action cleared their decisions. Message IDs are deterministic and
demo reply labels remain. Recognized accounts must exist for migration; corrupt
legacy records are already excluded by profile normalization. Migration commits
profile changes and history together, with rollback on failure. RP saves and
export/import preserve match records, DMs, translation variants and read markers.

## Workflow configuration

MatchMe uses Social Media message format/output channel **2**, JSON key
`matchMeApp`, and input header `[MATCHME DIRECT MESSAGE]`. On the first send, the
application finds LLM Prompt Switch nodes whose output 2 is named `Social Media`
and installs `MatchMe DM` at the first common free slot from **6** onward. A
standard workflow therefore uses slot 6. Fotogram slots 0/2/4, OnlyFriends slots
1/3/5, and all custom prompt text remain intact. A previously configured
`MatchMe DM` slot is reused without replacing its text. Its default text lives
in `chat/matchMePrompt.ts` and can be edited in the usual prompt editor.

The switch must be connected through the existing social-media workflow. If no
compatible switch exists, slots conflict, or all ten slots are occupied, sending
stops with a diagnostic explaining the configuration to fix. Matching itself
does not require an LLM. Saving the workflow/RP save retains the installed slot.

A direct reply must contain exactly one entry:

```json
{"matchMeApp":[{"from":"demo-alex","to":"storybook:<character-id>","message":"Hello!"}]}
```

Use the exact application-provided account IDs for `from` and `to`. Display names
are for presentation and are not the direct-reply identity contract. The reply
runs as the specified recipient and receives the confirmed match, public profiles,
recipient personality, this conversation's history, latest message and existing
RP time context. The other participant's private personality is not supplied by
the MatchMe context. Existing workflow context is still governed by the prompt's
in-world knowledge rules; MatchMe does not remove unrelated inputs from a custom
workflow.

Normal RP prompts receive active matches and public profiles as structured
context when matches exist. They and `Messenger_message` command passes can
initiate valid MatchMe messages. Account/match validation and correction replays
apply before output leaves the LLM prompt node. Direct runs additionally require
the exact bound recipient and sender. Final parsers and the central timeline
append operation check permission again. Invented accounts, self-messages and
unmatched pairs cannot become delivered app messages. MatchMe supports text and
emoji, without feed posts, comments, tips, voice or image-message attachments.

## Conversation behavior and validation

The UI reads `socialDirectMessage` timeline records with app `matchme`. IDs scope
conversations and drafts. Sending respects the global run lock, shows progress
and reports failed replies. The outgoing message is committed before the provider call, so provider errors
and cancellation retain it. Retry reuses that turn and its outgoing message ID;
outgoing and reply IDs are deduplicated at persistence. Changing the selected character or
conversation during generation does not change the run's participants. Incoming
messages use the shared per-character/per-conversation read markers and phone
badge mechanism. Embedded history links open the original conversation.

Non-UI tests cover all bundled matches, duplicate likes, inactive/unknown/self
accounts, ambiguous names, renames, conversation isolation, strict direct replies,
embedded/command permissions, legacy migration, RP-save round trips and custom
prompt slot preservation. The application and UI/E2E tests are not launched by
the implementation workflow.

Manual checks: create/edit a profile; like each NPC; open a Storybook account
with a profile; send text and emoji; switch conversations and characters during
a run; force a provider error and retry; check unread badges and embedded links;
save/load and export/import; restore earlier history and reset. Also check photo
selection, gallery-backed discovery photos, dark-mode compact layouts and
keyboard focus. Accounts without available photos show an unavailable state;
the matching policy is intentionally unconditional. The shared library fixture
and cross-app manual steps are documented in
`docs/architecture/character-container-v2.md`, Stage 4.
